# 提示词工程：怎样用提示词让 AI 高效

《生成式软件工程》第 02 讲。`slides.md` 是幻灯片与演示原文，`transcript.txt` 是逐句转写。

---

## 1. 原理：模型怎样"听"你的提示词

后面每一条技巧都从这三点推出来。

### 1.1 提示词 = 整个上下文

模型每一步做的是 **Pr[token | context]**：根据当前上下文预测下一个 token。Agent 的上下文远不止你打的那句话，按出现顺序是：

1. **System prompt**：Harness（Claude Code、Codex、pi 等）内置。
2. **多级 `AGENTS.md`**：用户级（全局）→ 项目级 → 子目录级，逐层叠加。
3. **Skills 索引**：只放每个 skill 的名字和简短描述；任务匹配时才加载完整 `SKILL.md`。
4. **工具定义**：工具 schema 以文本形式出现在上下文中。
5. **会话历史**：全部对话、工具调用及结果，线性累积。
6. **环境信息**：每次调用注入模型名、时间、cwd 等。
7. **你的 user message**。

所以"写提示词"实际是**上下文工程**：安排好上面所有东西，而不只是措辞。

> **重点**：代码库、你让它读的论文、工具输出，全都是提示词。它们对结果的影响可能比你那句话更大。

### 1.2 一步很浅，一串很深：chain-of-thought

- 输出一个 token 只走一次前向计算，深度非常有限（MoE 的"专家"只是表示空间上的分段函数，不是模型里坐着的多个小人）。一次前向不可能凭空完成复杂任务。
- 模型学会了**利用上下文思考**：不确定时先试一试，错了再输出 token 纠正；每个新 token 又成为下一步的 context。这就是 chain-of-thought（CoT）。
- 类比：人脑是有限状态机，有了纸和笔就成了图灵机。CoT 把上下文当纸笔——只是这张纸 append-only，写错了不能擦，只能靠注意力忽略。
- 推论：**找解难、验解易**（P vs. NP 的直觉类比）。只要中间进展或最终答案**可检查**，多写、多试、多修补就会稳定地变成能力（test-time scaling：用 token 换计算深度）。

### 1.3 注意力：指令一直"在场"，但会互相抢

- 每输出一个 token，模型都会"注意"到过去的上下文。全局 `AGENTS.md` 里的"用中文回答"会一直保有一定注意力。
- 专注写代码时，注意力集中在需求和已写的代码上，"用中文"的注意力变弱；写完代码转入总结时注意力转移，会发现并纠正之前的偏离。**每输出一个 token，就多一次发现偏航、拉回轨迹的机会。**
- "看得见"不是硬约束：长上下文中的信息不会被同样可靠地利用（Lost in the Middle）。一般**最后的指令最容易被遵循**，中间的最容易丢。
- 强化学习后的模型是"做题家"：上下文里任何指令不遵循都会受罚，所以它会拼命满足**每一条**指令——包括你不希望它满足的那条（见 2.5）。

## 2. 技巧：让模型知道"完成"是什么

### 2.1 把要求写成可验证的判据（verifier）

**做法**：给任务写一个能判断"做完没有"的标准，最好机器可验证（测试脚本、格式约束、可数的条件）。

**为什么**：模型被训练成持续推进 Pr[token | context] 直到**满足要求**。设生成轨迹为 τ，只有上下文里存在可识别的完成判据 V(τ) = 1，"继续干"和"可以交卷"才不只是两种高概率续写。

- 要求明确可验证 → 模型会不计代价一轮轮尝试，甚至自己装工具、上网查资料，直到通过。
- 要求不明确 → 模型可能认为已经"满足"，提前交卷。
- 一个足够好的模型，面对明确指令要么完成，要么承认失败（"这对我太难了，需要重新规划"），不应该幻觉或违背指令——前提是指令不过长。

> **重点（Rule of thumb）**：写清楚你的指令，承担一切"不明确"的后果。

**例 1：明确的 verifier 能做到超出大多数人的事。** 下面三条都不可能出现在训练数据里，模型靠 CoT 反复试错完成：

> 用中文写一个押韵的藏头诗，头是"计算机学院真牛逼"，要讲和动物相关的故事，"二零二六九月一日"八个字分别按顺序出现在八句里，位置无所谓。

模型的思考过程：先定韵脚 → 按顺序逐句填字 → 发现第三句又要放"二"、检查是否违规 → 不行就换韵脚重来。一次输出：

```
计逐二兔跃青麓，
算见零狐遁深谷，
机追二鹿穿林雾，
学唤六猪共食黍，
院中九鸡争米粟，
真如月下老牛步，
牛背一鸦栖如故，
逼近日落各归宿。
```

> 写十八字的一句话，全部有相同的偏旁或部首，要有实际意义和故事性。

输出示例："洪涝淹没江港渔浦，油污漂浮，沈涛泅渡济溺。"（不计标点 18 字，全带"氵"）

> 写一大段话（文言文），要求全部同一个音，也要有实际的故事性，不能用《施氏食狮史》和《季姬击鸡记》原文，原创一个有现代背景的。

**例 2：verifier 本身也要严谨。** "偏旁"是字形构件，"部首"主要是检字分类，二者不等价。要机械验收，应写成"**18 个汉字都含同一可见偏旁**"。

**难以 verify 的任务仍然难**：例如"讲得好的课"——好是多方面的，要有节奏和起伏，写不成明确判据，AI 目前做不好。在有明确判据的部分，把 AI 当能力的放大器；没有判据的部分，人还得自己把关。

### 2.2 补全 Intent → Spec → Impl 之间的空白

**做法**：不要只给意图（intent），把规格（spec）写出来：用什么实现、用什么资源、怎样算对。

**为什么**：Intent → Spec → Impl 每一层的空白都会被模型用自己的默认值填上，漂移逐层放大。你要 C++ 它给了 Java——你说过 C++，一眼就能看出错；你没说，它写 Java 就是"合理"的。

**例：一句话生成赛车游戏 / CS:GO。** 模型做得很逼真（物理、碰撞、后视镜都有），但不是你脑子里那一个——它补不全你脑中模糊的约束。如果你写明"**复用真实地图和美术资产**"，它会去 OpenStreetMap 下载开源地图（指定校区地图文件格式，它能把校区建模出来），并使用公开的车辆、城市、树木素材；不写，它就以为一切都要自己生成。

> **重点**：明确意图需要**产品领域**知识，写出设计需要**软件工程**知识；实现反而大多可以交给 AI。这两部分是你的价值所在。

### 2.3 用具体约束压缩解空间，不要用形容词

**做法**：给出可组合、可检查的具体选择（颜色、字体、栅格、留白、组件、参考物、后处理），而不是"现代""高级""不要 AI 味"这类形容词。

**为什么**：形容词几乎不排除任何候选。两个称职的实现者都能严格照做"现代风格"，却交出完全不同的页面——这仍然只是 intent。模型的品味基本固定，不加约束时会朝同一个方向发散，结果就是"AI 味"。"不要 AI 味"它也不知道怎么遵循。

**例：个人主页。**

- **Bad（把品味留给默认值）**：
  > 我是蒋炎岩，根据我的公开信息，制作一个现代风格的个人主页首页……

  结果：做工精致、滚动和浮动效果都好，但 AI 味很重。
- **Better（压缩合法解空间）**：用**具体**风格、**具体**样式和排版——比如"一个真正的终端：背景色 X、前景色 Y，支持管道；xterm.js 渲染完成后做一次后处理，让字形略不工整，像打字机打出来的"。结果：一行代码没写，页面却没有 AI 味。

> **重点**：关键不是多写几个形容词，而是让选择可组合、结果可检查。要写得出具体约束，平时就要积累：看到好的网页/设计时记下"它好在哪"（例如两个按钮之间用了不常规的间距）。

### 2.4 少用角色扮演咒语，直接写标准

**做法**：不写"你是一个资深 XX 专家"，而是把评判标准、证据要求、反证步骤写进上下文。

**为什么**：GPT-3.5/4 时代指令遵循差，"你是 XX 专家"某种程度上是在 hack self-attention，让模型模仿专家说话。CoT 成熟之后，只需把明确的 verifier 写进上下文，模型一定看得到、一定会去满足。角色设定主要改变的是先验、语气和输出格式，**不会凭空补上审稿标准、证据链和反证程序**——换上 reviewer 的制服，不等于学会了 review。

**例（Bad）**：
> 假装作为 ICSE'27 的审稿人 icse27-901.pdf，我应该接收它吗？写一个 1000 words 左右的 Review.txt。

好的写法见 3.2。

### 2.5 控制指令数量：指令会抢注意力

**做法**：全局规则（回答语言、commit 规范、结尾写 recap）放进 `AGENTS.md`，但只放真正需要的；纠正某个坏习惯前，权衡这条新指令带来的代价。

**为什么**：模型会拼命满足每一条指令，指令越多压力越大，上下文中的每条指令都在争夺注意力。

**例：被"过度遵循"的指令。**
- 人："要白色背景，不要半透明效果。"
- AI 写进代码：`// 白色背景（不要半透明效果）` 😂

它知道这句话重要，却没意识到这是"人的要求"，不该写进代码。为此在 `AGENTS.md` 里加"注释该怎么写"的规则可以纠正，但新规则本身又污染了上下文——这是 trade-off，没有通用解。长 skill 里堆满指令，在 AI 看来和写藏头诗差不多难。

**例：全局指令的正常用法。**
- `AGENTS.md`：用中文回答（即使用英文提问，回答也是中文）。
- `AGENTS.md`：git commit 里不要写 "Copiloted by Claude Code"。
- `AGENTS.md`：结尾必须写一段 Recap。

> **重点**：网上拿来的 skill 第一次用常有改进，多用几次就容易陷入"越改越不对"。陷进去时，回到自己写指令：想想 CoT 和注意力怎么工作，看它注意到了什么、得出了什么，做一点粗略的可解释性分析，再写 prompt。

## 3. 技巧：防止上下文把模型带偏

### 3.1 认识上下文污染

逻辑自洽的材料对注意力的"污染"极强。论文"a 所以 b 所以 c 所以 d"环环相扣，模型读完就站到了作者的立场上。

**例（Bad）**：
> 读一读 paper.pdf 帮我做个总结。

结果：总结基本就是作者的观点，原样复述。教科书章节、陌生项目同理。接着再追问，模型会变成"墙头草"——你说好它就说好，你说不好它就说不好；还喜欢在不重要的点上大做文章（"实验还可以再加强"）。

**操作细节**：要读的文件放到独立目录（如 `/tmp/papers/`）里打开，避免项目里的 `AGENTS.md` 等无关上下文混进来。

### 3.2 先对齐立场，再让它推一步

**做法**：
1. 先把模型拉到**你的立场**上，就"已知的东西"达成共识（grounding）。
2. 再让它**基于这些事实往后推一步**。一步推理是 AI 最擅长的，而且每一步都可检查。

**例：审稿 / 读论文，逐步追问。** 下面是一组实际有效的追问序列：

> 我现在是审稿人，不确定这个论文的贡献。

（模型把贡献拆成 5 项逐项评判——比"总结一下"好，但仍在作者给的框架里打转。）

> 我可能不能完全信任作者，虽然大概率也是诚实的，也有代码实现，可以运行。还是想评估一下研究贡献。

（模型转入"怀疑模式"：用记忆核对论文里的事实断言并标置信度，把贡献分成"可复现验证的"和"只能信叙事的"——仍然局限于"信不信作者"。）

> 应该这样：我们站在人类已知的知识边界上看这个问题。这不是一个完全老的问题——相关的东西是什么？解决到什么程度？这个工作试图解决哪些不一样增量的问题？

（关键一步：模型画出领域的知识地图——已有的四条技术路线各自做到哪、缺口在哪——再判断论文填的是不是真实空白，增量里哪些是方法贡献、哪些只是工程包装。）

> 软件状态的可视化，这是这个 paper 要解决的。那为什么说现在的工作都有一个无法实际使用的痛点？这个文章，可能只限于 linux kernel，但又是怎么能往前解决一点的？设计的合理性在哪里？

（在已对齐的边界上继续推一步：痛点 → 贡献边界 → 设计是否针对痛点。）

> **重点**：三问模板——**相关的东西是什么？解决到什么程度？这个工作的增量是什么？** 适用于读论文、读技术方案、评估开源项目。

**判断逻辑链是否断开**比挑实验细节更重要。例：论文要优化 A，A = A1 + A2，A1 占 99% 的时间，它却去优化 A2——局部论证都成立，整体没有意义。让 AI 审东西时，引导它检查这种链条，而不是"实验不够充分"。

### 3.3 学习时：告诉 AI 你在哪里

**做法**：告诉 AI 你学到什么程度、编程水平如何（可以长期维护一个 memory 文件），让它**从你已有的知识出发**解释。

**例：学链接与加载。**
> 我有一个 .cpp，有一个程序可以把它变成 .exe，这不就结束了吗？为什么还需要链接？

从你能理解的那个点出发，让它往前推一步，而不是让它从教科书第一页开始讲。讲得听不懂时直接要求"说人话"，多轮对话里先同步共识，再一起把推理链搭起来。

### 3.4 费曼法：让 AI 当学生

**做法**：先把 AI 当老师，问到自己以为懂了；再反过来：

> 你现在扮演学生，假装什么都不懂，我来把这个东西讲给你听。你检查我的逻辑哪里有错有漏，随时纠正我。

正着一遍、反着一遍，概念就清楚了。AI 不会嫌你菜，可以任意追问。

### 3.5 立即动手：问最小的问题

AI 把"启动一次尝试"的成本压到很低：推导不想验算、数据通路没看懂、链接没搞明白，都可以立刻开始问。但 AI 消灭的是"先试一下"的边际成本，不替你判断真伪：

> **重点**：提出最小问题 → 做最小检验 → 看反馈 → 更新理解。

## 4. 技巧：让 Agent 读代码、回答"为什么"

### 4.1 直接让 Agent 检查它自己

**例**：想知道上下文里有什么，直接问 agent：

> 老师上课的时候说 agent 的上下文里不仅是一两个提示词，你能检查一下你的上下文里都有些什么吗？

它会列出 system prompt、各级 `AGENTS.md`、skills 索引、工具 schema、会话日志（含 token 用量和 `cacheRead`：前缀被缓存，只为增量付费）和环境变量。Agent 能看到自己的上下文和日志，只要没有明确禁止，就能读出来。

### 4.2 把好奇的细节变成一次代码阅读

**做法**：遇到"这是怎么实现的"，下载源码，描述你观察到的现象和你的猜测，让 agent 去读代码。

**例：Codex 为什么有些命令不弹确认？**
> 我留意到一个很有趣的问题：在调用 bash 的时候，有的时候会向用户确认，有的时候不会，有一个风险的判定。风险其实是一个很难的问题，你并不知道具体的命令语义是什么。所以你是做了分析，还是让大模型给了风险的评级，还是别的什么方法？读一下相关的代码。

得到的结论：
- **模型提议，Harness 决策，操作系统收口**：模型只生成"想运行什么"；sandbox 决定技术上能碰什么；approval policy 决定何时暂停询问。
- 规则按**完整参数列表**匹配 `allow` / `prompt` / `forbidden`；shell 命令链先做语法解析再逐条检查，**最严格的结果获胜**。
- 不在白名单里的命令，Harness 会**注入一段安全评估 prompt**（guardian），让模型给风险评级——这本身也是提示词工程。
- 早期 Codex 把 `rg` 当只读安全命令，漏掉了能触发外部程序的 `--pre`、`-z` 参数（CVE-2025-54558）：安全属性属于完整调用，不属于命令名。

接着可以追问：
> 把安全评估的 prompt 打印出来看看。

### 4.3 怀疑 AI 的解释时：改 prompt，看行为

**做法**：不确定 AI 对机制的解释对不对时，让它**修改那段 prompt**——让原来会放行的变成拒绝，或者反过来——再观察行为是否真的变化。行为变化就是证据。

## 5. 技巧：长程编程任务

### 5.1 长程能力来自闭环反馈

- 后训练只要有反馈信号就能强化学习（答对奖励、答错挨揍），逼出了很长程的代码能力，顺带把指令遵循也解决了。
- Long-horizon 不是一次想得特别深，而是**闭环控制：尝试 → 编译/测试 → 观察 → 修复**。真正变长的是"出错以后还能拉回来"。
- 代码世界特别适合：构建、测试、benchmark 都能反复给出便宜的判分信号，像 AlphaGo Zero 的棋盘。
- 模型有一种"着急"的倾向：尽快满足判据就结束（规划太长做不完会被罚）。它最擅长的粒度是"帮我把这个 PR 做了"。

> **重点**：给 agent 便宜、可重复的反馈信号（编译、测试、benchmark），它就能自己跑很久。

### 5.2 防 reward hacking

测试只覆盖表面行为时，"坚持"会变成 reward hacking：不是逼近真实目标，而是把公开分数刷满。

**做法**：保留 held-out tests（不给 agent 看的测试）和独立 review。

### 5.3 代码库本身就是提示词

**现象**：从零做产品，PoC 很快出来；往后一个个加功能，到某个时间点开始翻车，成本越来越高。反而在 Linux 内核、Android Runtime JIT 编译器这类大型、复杂、维护良好的系统里，AI 游刃有余——人类在这里常被劝退（点进十层函数调用，最后只有一句 `x = y`）。

**为什么**：和论文污染正好相反。高质量代码库里，要写的功能多半已有几处类似实现；self-attention 加载几十个文件后立刻找到它们，照着学（in-context learning）：该调哪个 helper、按什么顺序上锁。而如果项目起步时没有工程纪律，AI 就学会了在 slop 上无限叠加。上下文压缩 = 降智。

**做法**：
- 新项目尽早建立工程纪律（结构、规范、测试），给 AI 好的范例去模仿。
- 一个未经实验的猜想：在代码库里放一个相近领域、优雅成熟的高质量系统，先让 AI 读这份代码，再实现你的需求，可能得到质量更高的软件。也可以把多个优秀项目的设计经验提炼成文档放进来（类似《A Philosophy of Software Design》）。难点在于不同设计会冲突（松耦合发消息 vs 统一 gateway 查表），可能需要放入多套设计，让 AI 多轮迭代收敛到一种。

### 5.4 研究型任务：别让 agent 证明你的 idea

**例（失败）**：优化一个符号执行引擎，有一个原始 idea。把 benchmark 和想法丢给 GPT-5.6，跑了大量 token，没有结果，也无法判断 AI 的反馈对不对。

**原因**：
- 上下文里一句"我想证明 A 方法有用"让模型成了 reward hacker：忘掉研究的全局，在小 microbenchmark 上做微小改动，给出无意义的正负结论。
- 缺的不是 token，而是**便宜、局部、可归因的反馈**。一个总 benchmark 分数几乎不提示下一步方向。
- "没变快"可能来自 path explosion、solver、缓存、内存、搜索策略、实现 bug 或环境噪声，agent 不知道该强化哪一步。
- Agent 被训练成"把任务做完"，研究却允许最好的结论是"**原始 idea 不成立**"。没有可证伪的假设，它会把错误的想法实现得越来越完整。

**做法**：
1. 先 profile，找主导瓶颈。
2. 把 idea 改写成一句**可证伪的预测**。
3. 造几十秒就能出反馈的 microbenchmark。
4. 再做 baseline 和 ablation。
5. 从真实工具和 state-of-the-art 算法出发：哪怕 benchmark 跑几小时超时，超时里的搜索路径也会揭示哪类程序结构对现有方法不友好。（参照 KLEE：把问题拆成搜索策略、约束缓存、independent constraint sets 等机制，分别测量。）

### 5.5 人的精力花在哪

- 盯着 session、跑偏就立刻注入领域知识纠正，通常完成得更快；不盯、多给 token，大多也能完成。精力有限，要放在收益最大的地方。
- 纠正 AI 会带来"我比 AI 有用"的心理满足，要警惕这种假努力。
- 原则：不知道的东西，自己去弄懂；知道怎么做、AI 能做好的，放手让它做。
- 你得知道上下文里每样东西会对 AI 产生什么影响，才能把它引到对的方向上——这需要处理器、操作系统、编译器、数据库这些知识。没有概念，就提不出正确的问题。

## 6. 技巧：开放问题用算力换智力

### 6.1 "给我几个方案"为什么不够

- 问题和路线都想清楚了，CoT 就能解决；难的是**在不确定性中探索**。
- 模型被训练成"完成任务才有奖励"，所以会给出**有限**的方案。验解容易、找解难，为了交卷它只能做有限搜索，更好的方案可能被藏起来。
- "给我几种"只规定了停止条件 k，没有规定覆盖率——这就是 Herbert Simon 说的**满意化（satisficing）**：搜到"够好"就停。
- CoT 用算力换**深度**（沿一条路多走几步）；并行枚举用算力换**宽度**（让更多轨迹进入低概率的尾部）。
- 探索的瓶颈常常不是"想不出"，而是模型太早认定"已经够了"。

### 6.2 把灵感改造成搜索

**例（Bad）**：
> 给我小孩取一个蒋姓，好听、又有寄托的名字

结果给了 8 个分好类的名字（蒋知行、蒋既明、蒋闻道、蒋一苇、蒋若谷、蒋清和、蒋望舒、蒋照临），质量不差，但带着模型自己的偏好；别人用同一个模型也会拿到同样的名字——孩子就成了 AI 时代的"子涵"。

**做法（Better）**：
1. **定义探索空间**：典故 × 音韵 × 方言 × 时代感。
2. **要求枚举**：可以先选音，筛掉不好的音；再逐字选；比如喜欢《诗经》，就从《诗经》里系统地找。
3. **独立采样再汇总**：多个 sub-agent 分别生成，别让它们一开始就互相抄。
4. **sub-agent 审查**：查出处、听谐音、看重名。
5. **设一个反对者**：专门挑毛病。

> **重点**：选择质量 ≈ 覆盖率 × 评估分辨率。枚举负责提高覆盖率，审查负责提高分辨率。把大空间里的开放问题切成互不重叠的子空间，每个子空间就成了有 verifier 的明确问题——算力越多，智力越大。代价是烧 token。

这和科研的文献调研是同一套方法：先穷尽相关的工作，再做判断。AI 为了尽快完成任务不会主动付出这种代价，要由你在 prompt 里把搜索过程规定出来。

## 速查表

| 场景 | 不要这样 | 要这样 |
|---|---|---|
| 写需求 | "做一个 XX" | 写明实现语言、资源、怎样算对（verifier） |
| 要设计感 | "现代风格""不要 AI 味" | 给出具体颜色、字体、排版、参考物、后处理 |
| 设定身份 | "你是资深 XX 专家" | 写出评判标准、证据要求、反证步骤 |
| 全局规则 | 把所有偏好都塞进 AGENTS.md | 只放必要的；新增规则前权衡它抢走的注意力 |
| 读论文/方案 | "帮我总结一下" | 先问：相关工作是什么？解决到哪？增量是什么？再推一步 |
| 学新概念 | "给我讲讲 XX" | 告诉它你会什么，从你懂的那一点问起；再用费曼法反讲 |
| 好奇实现 | 凭印象猜 | 下载源码，描述现象和猜测，让 agent 读代码 |
| 怀疑解释 | 直接相信 | 改 prompt，观察行为变化 |
| 长程编程 | 一句话从零生成 | 给可重复的测试/编译反馈；保留 held-out tests；尽早建立工程纪律 |
| 研究探索 | "证明我的 idea 有用" | profile → 可证伪预测 → 秒级反馈 → baseline/ablation |
| 开放问题 | "给我几个方案" | 定义空间 → 独立枚举 → sub-agent 审查 → 反对者挑错 |

## 术语

- **Pr[token | context]**：模型每一步的条件概率分布；context 是整个上下文。
- **上下文工程（context engineering）**：组织 system prompt、AGENTS.md、skills、工具、会话历史、环境信息和用户指令的整体工程。
- **Harness**：包住模型的 agent 框架，负责 system prompt、工具、sandbox 和审批。
- **Verifier / V(τ)**：判断生成轨迹 τ 是否完成的判据。
- **Chain-of-thought（CoT）**：把上下文当"纸笔"，用 token 换计算深度。
- **Test-time scaling**：推理时多花算力换更好的结果：深度靠 CoT，宽度靠并行枚举。
- **Reward hacking**：优化看得见的分数，而不是真实目标。
- **Satisficing（满意化）**：搜到"够好"就停。
- **AI slop**：同质化、低质量的 AI 生成内容。
